# 网页最小可玩 Demo：PixiJS 实施规划

更新：2026-10-07。状态：**用户已批准技术方案，网页实现、性能对比和网页验收尚未完成。**

用户在讨论网页版引擎后明确选择 **PixiJS + TypeScript + C/WebAssembly**，并要求更新项目规划。本文记录这项技术决定；当前主玩法继续依据 [Boss 规划](boss-mode-plan.md) 和已有 Demo 的获准规则。完整原规范及原 PDF 保留为原始依据。

## 1. 本轮目标与基线

把已有 Windows/EasyX Demo 迁移为可以通过浏览器试玩的最小版本，用于验证操作、攻防、共享能量和四招用途。第一条完整招式是中间里程碑；本轮交付仍须四招、学生反击、胜负、暂停和重开。

用户已提供 `ustc-danmaku-demo-package/` 及同名 ZIP，内含源码和编写、调试记录。本地还存在 `demo/minimal-playable` 分支；规划更新时其已提交 HEAD 为 `753a9f6`。这些是待核对的迁移来源，**不代表 GitHub 主线已包含相同源码，也不代表已独立验收**。旧报告包含修订指纹和未执行项，不能将其结果继承为 Web 验收。

实施母代理先核实当前源码与包的差异、未提交修改、构建入口和历史失败，选定并记录一个可复现的基线。优先复用 `core/`、`ai/`，不得只因换前端就重新编写碰撞、四招、AI 或胜负规则。若当前 checkout 尚无 Demo 源码，先从已提供来源核对并纳入基线，再开始网页任务；不要照旧提示词从零再造游戏。

本轮不要求完成机器学习训练平台、模型训练、联网、排行榜、课程全量计分、GA、旧 Q 表、技能场或擦弹系统。网站对外托管是独立交付步骤；先产出可本地访问和可部署的静态包。

## 2. 已确定的技术分工

| 层 | 方案与职责 | 边界 |
| --- | --- | --- |
| 游戏核心 | C99/C11；既有 `core/*.c` 与 `ai/*.c` | 唯一裁决运动、扫掠命中、能量、攻击计划、学生脚本、随机数和终局 |
| 网页核心构建 | Emscripten 将同一批 C 源码编译成 Wasm | 不包含 EasyX、Win32 输入、窗口或原生日志文件代码 |
| 跨语言适配 | 薄 C 导出层 + TypeScript 客户端 | 明确版本、容量、有效期和错误状态；按批读取显示数据 |
| 游戏画面 | PixiJS 8.x，首版使用 WebGL | 只读显示快照；角色、弹幕、预警和视觉反馈均不裁决物理 |
| 网页交互 | TypeScript；菜单和 HUD 优先 HTML/CSS | 输入、布局、暂停、开始、重开和错误提示；不另写游戏规则 |
| 原生仿真与后续训练 | 同一 C 核心的原生无界面构建 | 可以按逻辑 tick 加速、重放和并行；不依赖 Pixi Ticker 或显示刷新率 |

前端构建建议使用 Vite。实施前冻结 PixiJS 的具体版本、TypeScript、构建工具、Node.js 和 Emscripten 版本，提交锁文件并记录实测命令。不得混用 PixiJS v7 与 v8 的初始化、Ticker 和粒子 API。版本冻结是实施阶段工作，本次未安装或验证工具链。

PixiJS 是 2D 渲染引擎，游戏流程需由项目组织；UI、音频等可按需要接入生态库。首版不引入通用 ECS、编辑器、重型 UI 框架或自制插件系统。若加入音频，遵守浏览器用户手势解锁要求，音效失败不阻塞游戏。

## 3. 迁移继续遵守的玩法

以下沿用提供的 Demo `docs/demo-rules.md` 中的已批准记录；接入源码时将完整规则记录纳入并核对，试验数值继续由同一 C 配置提供。

- 人类操作可移动 Boss，四招由玩家主动发出；共享能量自然恢复并封顶，成功请求扣一次，拒绝不扣、不排队。
- 鼠标朝指针位置移动、接近时减速，死区和键盘备用入口沿用基线；坐标按逻辑战场解释。默认逻辑画面 1280×720，战场 960×720，HUD 320 px。
- 同时只运行一招；接受时锁目标和预警几何，攻击沿用同一计划。网页预警不得重抽随机数或暗中改变攻击。
- 学生发射时瞄准 Boss 当时位置，直线弹不追踪；角色接触不伤害，普通弹不穿透，使用相对运动扫掠及已有稳定 ID 破平局规则。
- 同一 tick Boss 与最后一名学生同时倒下记 Boss 胜；无强制对局时限。仿真 `max_ticks` 仅作实验截断，不能转换成胜负。
- 攻击结束只清本招剩余 Boss 弹；学生反击弹继续按原规则处理。
- 本轮使用已批准的直线基础运动，不启用默认场力、`ddl 逆转` 或擦弹计分；学生是可复现脚本，不宣称经过训练。

已有规则记录中仍存在的歧义，例如锁定出生点后学生进入该位置时的安全复查、鼠标和键盘混用优先级，不因迁移自动获得新答案。沿用并标注基线的临时处理；涉及改变规则时核查用户已有答复，必要时集中说明具体场景。不要重问已批准的网页技术方案、同步死亡、反击方向或时限。

## 4. 桥接、输入和时钟契约

### C/Wasm 接口

母代理在并行前冻结接口文档和 C/TS 共有类型。至少提供初始化/重置、释放、固定 tick 推进、批量显示快照和诊断信息；这些是拟实施形状，不是现有已实现 API。

- 既有 `WorldView` 含指向核心内部的 C 指针，不能直接作为 JavaScript 对象。适配层导出活跃实体的连续数组、数量、血量/能量/攻击状态、公开预警和事件；不导出隐藏随机流或未公开的未来状态。已经公布的预警所需后续波次几何与时序允许只读投影；显示快照与 AI 观察分别规定可见字段。
- 固定容量与缓冲有效期写入契约；容量不足、版本不符或数据损坏须报错，不静默截断。`uint64_t` seed/实体 ID/计划 ID 使用高低两个 `uint32_t` 或明确 BigInt 契约，不能无条件转换成 JS `number`。
- TypeScript 从明确的偏移和布局读取数据，不猜 C 结构体对齐。Wasm 内存增长后重新建立 TypedArray 视图，跨帧保存的数据须复制或明确有效期。
- 每个 tick 推进后收集事件；同一显示帧追赶多个 tick 时汇总全部事件，不能只保留最后一个 tick。出招边沿消费一次，重复轮询不能复制一次按键。
- 前端按批读取快照，不对每一发弹逐字段调用导出函数。若公开预警信息不足，由核心提供只读几何投影，不在 TS 复制招式算法。

### 浏览器输入与唯一主循环

- 母代理维护唯一主循环。固定逻辑 60 Hz；显示帧可运行零个、一个或多个逻辑 tick，不能把 `Ticker.maxFPS=60` 当作固定物理时钟。
- 没有逻辑 tick 时保留未消费的出招边沿；追赶时只在约定 tick 消费，处理拒绝后不排队。暂停、重开、终局和失焦清理输入的方式需统一。
- CSS 缩放、留边、DPR 和 Canvas 尺寸均通过同一屏幕到逻辑坐标转换处理；布局变化不改变角色半径、弹速或碰撞坐标。
- 页面隐藏时自动暂停；返回后显示暂停状态，由玩家继续。恢复清零时间积压，不补隐藏期间的逻辑，不出现骤然连发。
- 短暂掉帧可按有界策略追赶；超出预算时明确暂停/提示并清理时间积压，不悄悄改变 tick 长度、弹速或训练记录。预算属于实现配置，记录实测依据。
- 键盘、右键暂停、重开以及焦点恢复按实际浏览器行为验证；只在游戏交互区域处理必要的浏览器默认行为。

## 5. 渲染和性能起点

首版使用普通 Sprite 对象池和共享纹理/图集，按稳定实体身份更新；复用弹池槽位不等于复用整局 ID。预警读取 C 的公开几何，界面按状态变化更新，避免每帧重建全部 DOM、文字纹理和复杂 Graphics。

先不依赖 WebGPU 或实验性 ParticleContainer。只有性能采样指向渲染瓶颈时，再采用粒子容器、专用批量绘制等措施。简单弹不逐个挂滤镜、交互事件、物理组件或独立更新回调。

800 发是当前池容量及压力检查目标，不是日常四招都会产生的弹量。压力夹具可以在单独测试场景中构造，必须标为夹具，不修改正式规则或当作实际对局证据。

不承诺“性能几乎不变”。分别记录 C 核心耗时、桥接/解码耗时、绘制及整帧耗时、帧时间分布、资源加载和内存；记录机器、浏览器、构建模式、分辨率、DPR、弹量和测试时长。网页首轮以目标设备流畅 60 FPS 为验证目标，不将“计数器显示 60”作为唯一性能证据。原生仿真吞吐单独报告。

母代理独占公共 C 头/TS 类型、规则配置、导出清单、依赖锁文件、前端构建配置、网页入口、公共样式、任务板和共享构建入口。W01 的构建文件须有单独授权，完成后收回写权限。每个文件同一时间一个写入者；孙任务必须是父任务范围内不重叠的小产出。总并发建议最多 4 个，包含母、子、孙。

共享 checkout 的分支切换、暂存、提交、推送和回退由母代理统一执行。子/孙不得操作共享 index，不得使用 `reset`、`clean` 或 `checkout --` 清理或回退他人修改；使用独立工作树时，在任务卡明确允许的 Git 操作及集成方式。

## 7. 交付与验收门槛

1. 固定基线可复现，已有构建失败逐项记录；迁移不会自动解决历史问题。修复与网页改动分别留下原因和证据，不覆盖旧调试记录。
2. 干净环境能构建 Wasm 与前端，通过 HTTP 本地访问；普通单线程方案不依赖跨源隔离。页面部署须正确提供 Wasm MIME 类型和资源路径，不能以双击 `file://` 作为验收入口。
3. 完成四招、学生躲避与反击、真实命中、自动目标、共享能量、可演示胜负、暂停及重开。临时桩和预录动画不算可玩版本。
4. 原生与 Wasm 在同配置、种子和逐 tick 输入下对照状态、事件及终态；比较稳定字段，不比较含指针/填充的结构体原始字节。浮点容差预先记录；离散事件/目标/胜负分歧视为失败，不扩大容差掩盖。
5. 实际检查零/多 tick 帧、按键与按钮重复、失焦、缩放、页面隐藏、暂停恢复、重开、终局和连续重新进入；记录测试方式和未执行项。
6. Release 构建在明确设备/浏览器上采样常规对局和 800 发夹具，报告帧耗时及分层成本；无法达到目标时留下可复现问题，不写性能等价结论。
7. 交付源码、依赖锁、构建说明、静态包、操作说明和独立验收报告。可先本地试玩；对外部署前确保产物和部署配置可供审查，不把“构建成功”写成“已发布”。

## 8. 对后续训练的影响

离线训练继续链接同一 C 核心的原生无界面构建，不让浏览器帧率或暂停决定训练时间。`sim` 脚本回放不是已经完成的 RL 环境；观察、动作、决策周期、奖励、重置、终止/实验截断、批量环境和模型导入仍须在后续阶段设计。

渲染快照只用于显示，不能直接代替学习观察。后续训练冻结核心、配置、对手策略和种子分组，依 [机器学习平衡规划](ai-balance-plan.md) 实施；网页用于真人试玩与回放展示。本次技术选择不批准训练算法、奖励系数或规则调参。
