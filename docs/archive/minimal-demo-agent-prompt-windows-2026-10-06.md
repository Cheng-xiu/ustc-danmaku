## 三 这个 demo 必须验证的体验

当前主玩法是：**人类操作可移动 Boss，主动选择四种招式，花费共享能量，对战会躲弹和反击的 AI 学生。** 在 Boss 血量耗尽前击倒全部学生。玩家应能判断“现在用小招解决威胁”或“等能量恢复，争取更好的大招机会”。

最终 demo 必须完成以下闭环：

- 启动后有简短中文说明，可以快速开始对局。
- 玩家可控制 Boss 移动，松开停止，斜向速度归一化，不能越过合法区域。
- AI 学生有独立位置、血量和倒下状态，会按可复现脚本移动、躲弹和反击。
- Boss 自动标记最近的存活学生；移动和瞄准分离，同距时按稳定 ID 决定目标。
- 四个招式按钮由玩家主动触发；不按就等待和蓄能，不自动轮换。
- 共享能量有上限，按逻辑时间自然恢复；成功接受请求扣一次，拒绝不扣、不排队。
- 招式按“接受请求 → 预警 → 攻击 → 可再次选招”运行，同一时间只执行一招。
- 四招都有真实攻击效果及不同战术用途，不能只有名称、颜色、按钮或数值差异。
- 学生弹可伤害 Boss，Boss 弹可伤害学生；命中、失血和倒下有清楚反馈。
- 能分别演示 Boss 获胜和失败；同一步双方倒下按用户确认规则处理。
- 暂停冻结全部逻辑，继续后没有积攒的突发追赶；结束后逻辑停止，可以重开。
- 重开清除旧弹幕、攻击计划、目标、能量、AI 状态、无敌计时和输入边沿，恢复同一场景的初始状态。
- 可从源码构建，交付可运行包、操作说明、实际验证记录和已知问题。

第一条能玩的一招闭环是中间里程碑，最终本轮 demo 仍需四招，才能验证资源取舍。无法完成时如实报告“开发中原型”，不能把两招或静态界面当成本任务完成。

本轮明确延后：GPA、压制率、复杂成绩单、固定四阶段难度、GA、强化学习、旧 `Q[36][4]`、四档训练快照、在线自适应、联网和排行榜。AI 学生使用可复现脚本即可，不假装经过训练。保留可供后续测试和训练复用的纯 C 核心，暂不建训练平台。

暂不启用多学生 `ddl 逆转` 技能场及擦弹计分，记录为 demo 范围取舍。当前规划要求在启用前明确多场叠加和逐学生事件归属；不得静默创造叠加规则。默认场力是否仍作用于 Boss 弹也属于规则确认项，不能把“技能未启用”偷换成“原场力已全部删除”。如果用户要求本轮纳入技能，先确认这些交互，重新拆任务与验收，不能直接套用旧单学生实现。

不要给 Boss 主玩法重新加入固定六秒选招、默认招式循环或未经确认的独立冷却。招式可以有不同的预警和攻击时长；这些时长不等于旧固定选招窗口。不要沿用原 120 秒生存通关、固定上方 Boss 和学生向上射击作为新规则。

## 五 工程边界和共享接口

### 5.1 技术栈

- 核心使用 C99 或 C11，`core/*.c` 和脚本 AI 必须由 C 编译器编译；禁止仅改扩展名后仍用 C++ 编译核心。
- Windows 图形沿用 EasyX。适配确有需要时，窗口、输入、绘图使用少量 `.cpp`，经 `extern "C"` 链接纯 C 接口。头文件同时可被 C 与 C++ 包含。
- 核心不包含 EasyX、Windows 输入 API、窗口 API、墙钟查询或 C++ 容器。核心内不绘图、不直接写日志文件。
- `game`、`sim` 和测试链接同一批核心及脚本 AI 源码，读取同一规则配置。禁止为 headless 工具再写一套近似碰撞、能量或招式。

- 母代理检查本机编译器、架构、EasyX 版本和库路径，先完成最小链接验证。缺少 EasyX 时可继续独立 headless 工作；不要自行换成网页、Python、Unity 或另一个图形库。
- 构建应提供明确可复用命令。CMake 可用时采用 CMake，使用可配置 EasyX 路径，不提交个人绝对路径；没有时选择一个简单可复现的构建方式，不同时维护多套未经验证的方案。

### 5.3 接口冻结

母代理在并行编码前创建 `docs/demo-interfaces.md` 和可编译的公共头文件。至少明确：

| 对象 | 必须确定的内容 |
| --- | --- |
| `DemoConfig` | 版本、场地、各角色参数、能量、四招参数、学生反击、容量、已批准裁决 |
| `World` | 整数 tick、状态、Boss、学生、弹池、当前攻击计划、独立 RNG 流、当步事件 |
| `BossInput` | 归一化移动、一次按下的招式请求；暂停/重开由外层状态管理 |
| `StudentAction` | 移动意图和批准范围内的反击请求；不能直接写世界 |
| `AttackPlan` | 唯一 attack ID、招式、目标 ID、锁定位置/方向、完整波次和几何参数 |
| `Projectile` | 唯一 ID/世代、所属阵营、来源角色、attack ID、前后位置、速度、半径、伤害、寿命 |
| `StepEvents` | 接受/拒绝、预警/生成、命中、倒下、终局等，带 tick、来源和目标 |
| `WorldView` | 渲染、AI 和日志的只读数据；不暴露未来隐藏状态 |

可以采用下面的接口形状；具体签名在第一波次一次冻结，不能让各子代理分别猜测：

```c
bool world_reset(World *world, const DemoConfig *config, uint64_t seed);
void world_step(World *world, const BossInput *input);
void world_make_view(const World *world, WorldView *out);
void student_bot_choose(const StudentObservation *obs,
                        StudentBotState *bot, StudentAction *out);
bool pattern_make_plan(const PatternRequest *request,
                       const DemoConfig *config, Rng *rng, AttackPlan *out);
void pattern_emit(const AttackPlan *plan, uint32_t attack_tick,
                  ProjectileSpawnBuffer *out);
```

学生 AI 的固定决策调度、动作保持与反击计时放在共享 C 仿真调用链，由 `world_step` 统一协调，图形端和 sim 不各自决定调用频率。AI 使用自己的状态/RNG，接收只读观测，产出意图；世界移动和命中仍由核心执行。

函数返回和错误处理也要写清：空指针、非法配置、空目标、计划容量不足、弹池不足不能越界或静默继续。公共接口修改先由母代理判断，更新版本、所有受影响任务卡和编译检查，再恢复并行任务。

### 5.4 时间和输入

- 使用整数逻辑 tick，`dt=1/60` 固定；所有预警、恢复、反击、无敌和终局在同一逻辑时钟上。
- 图形主循环使用固定步累积器。掉帧可以暂缓绘制并追赶逻辑，不扩大 dt，不静默丢弃 tick。
- 暂停不调用推进函数，恢复时清理墙钟累积，暂停期间不保留出招请求。
- 招式输入从松开变为按下时产生一个请求。一次显示帧追赶多个 tick 时，这个请求只能被消费一次，不能每个补帧重复扣能量。
- 多按钮同时按下、键盘与手柄同时存在、失焦和恢复的行为在输入契约中确定。默认建议单请求、稳定按键优先级、失焦暂停，若改变玩法需纳入确认。
- 摇杆死区、幅度和键盘斜向归一化由适配层处理；角色速度和边界由核心处理。
- 无强制时限时，sim 的 `max_ticks` 仅是防卡住的实验截断，结果记为 `TRUNCATED/未完成`，不能自动记胜或负。

### 5.5 攻击计划与预警一致

只锁定 `target_id` 不够。接受请求时，核心一次生成完整不可变 `AttackPlan`，并按同一操作扣除一次能量。预警和实际攻击都读取这一计划。

- 环弹锁定生成原点、各圈时刻、缺口及其变化计划。
- 课表锁定各波列位置、通道与移动/连接计划。
- 金矿锁定矿点、扇面方向、波次和出生安全检查。
- 淋浴锁定扫描方向、各波位置和缝隙计划。
- 预警期间 Boss 移动、学生移动或目标倒下，都不能让本招重新选目标、迁移原点或重抽随机几何；下一次合法请求才重新选存活目标。
- 动态攻击可以展开和移动，未来变化必须已由计划确定，并用可理解的预警说明。
- AI 可读取当前向玩家公开的预警，不得读取隐藏的完整未来波次、未来弹位置或世界随机数。
- 不足能量、忙碌、无目标和计划错误都有明确拒绝码，不扣能量、不排队、不自动补发。
- 出生安全距离的检查时刻和学生后来走入锁定出生位置的处理必须采用第四节确认后的契约。遇到几何锁定与安全距离冲突，不自行挪点、漏发波次或创造无预警命中规则；保留诊断并交母代理处理。测试覆盖预警期间和后续波次前的这类移动。
- 攻击结束与残弹按获准契约处理，不照搬每六秒清全场。

### 5.6 碰撞与确定性

Boss 弹对学生、学生弹对 Boss，均检查该 tick 双方相对运动线段与半径之和；高速弹从一侧穿过另一侧也必须命中。零长度相对运动分支避免除零。多目标时按获准的穿透规则和最早交点处理，不能因为遍历顺序改变结果。

有效受击、无敌、击倒和终局顺序写成一个核心契约，覆盖同 tick 多弹、多个学生倒下及最后学生与 Boss 同时倒下。单学生倒下后退出后续行动，不能触发学生全灭；倒下事件只发一次。

弹池 ID 可追溯，不能把复用下标当整局唯一 ID。容量校验要使批准的四招波次能够兑现；运行溢出时保留明确错误事件和诊断，不能偷偷少发弹后仍宣称预警一致。

使用明确算法的 PRNG，可用原规范的 SplitMix64 派生 world 和 bot 流。不要用墙钟、平台 `rand()`、渲染或日志消耗的随机结果影响世界。同构建同配置同种子同输入应得同事件序列；不承诺未经测试的跨平台浮点位级一致。

## 六 母代理调度规程

先检查执行环境最大代理数量。建议总计最多 4 个活跃代理，包含母、子、孙，因此一般同时开 3 个子任务。平台上限更低则降低并发；提高并发需要确认文件独立且资源足够，不能只为了用满模型。

同一任务通常最多 1 至 2 个孙任务，全部计入总并发。简单任务无需派生。没有工具层禁止递归功能时，在孙代理系统/任务提示词中禁止调用创建、委派、再启动代理的工具，并由母代理和子代理审查代理树。

### 6.3 集成和 Git

- 检查并保留用户现有未提交修改。使用独立工作分支，例如 `demo/minimal-playable`；如同名已存在，检查用途并复用适合的分支，不覆盖已有工作。
- 默认一个共享 checkout、文件独占、母代理集中提交。子代理和孙代理不得执行 `git add/commit/push/switch/reset/clean`，不得修改共享 Git 索引或分支。
- 本提示词采用共享 checkout 和集中提交。若平台只支持独立 worktree，母代理先说明环境差异，统一制定并替换任务卡与通用提示词中的 Git 权限和集成规则，再派发任务；不能同时发送“禁止提交”和“各自提交”的矛盾指令。不强推、不丢弃用户修改。
- 依赖安装、头文件、配置、构建清单和公共入口由母代理统一处理。
- 每个任务交回后检查 diff、接口、越界改动和实际验证，再接到主闭环。不要等所有任务结束才第一次链接。
- 发现接口冲突先暂停相关写入，明确唯一负责人，修好接口后重新派卡。禁止各代理互相追着改签名。
- GitHub 若需登录，调用环境支持的交互登录流程并弹出浏览器/登录窗口，让用户自行完成；不要求把密码或 token 发到聊天。没有弹窗能力时说明具体限制，不声称已弹出。仅在明确认证错误时触发，公开拉取成功无需登录。
- 本任务完成后可以提交到工作分支、推送并创建 draft PR 供审核。默认不合并到 `main`，不发布正式 release；发布/合并按用户已有明确指令处理。

## 七 子代理任务清单

以下是 20 个小任务，可以分批创建、重复使用空闲代理承担后续任务，不要求同时启动 20 个代理。所有子代理模型均为 `a6api/deepseek-v4.1-flash`、`depth=1`。下面给出专属说明；派发时必须连同第八节通用提示词及填好的任务卡发送。

### S01 仓库与规则只读审查

目标：确认当前代码/文档状态，区分旧方案和当前 Boss 模式，形成缺口清单。先完整阅读权威资料，再检查是否已有代码和构建入口。

写权限：无。向母代理回报现状、可复用内容、关键未定规则、相关路径和章节。不能自己确定同死裁决、输入设备或四招档位，也不能去询问用户。可派一名只读孙代理核对技术章节，须先取得槽位。

验收：明确指出主玩法与旧六秒/Q 表/120 秒方案的区别；事实与建议分开。母代理据此完成规则确认单。

### S02 确定性随机数

文件：`core/rng.c`、`tests/test_rng.c`。头文件由母代理提供。

目标：实现指定 PRNG、独立流派生和状态重置。不能使用时间或全局 `rand()`。实现不能受输出日志或绘制影响。

验收：同 seed 同序列，重置恢复序列，world/bot 流互不消费；固定测试向量与文档算法一致。可将测试向量独立核对交给只读孙代理。

### S03 扫掠碰撞

文件：`core/collision.c`、`tests/test_collision.c`。

目标：纯 C 相对线段碰撞与必要的最早交点计算。只做数学判定，不扣血、不移除弹幕、不决定胜负。

验收：静止、相切、错过、双方移动、高速穿过、零相对运动均覆盖；返回值无 NaN，顺序由母代理契约规定。可将独立边界测试交孙代理，但不共同写同一测试文件。

### S04 角色移动和生命

文件：`core/actors.c`、`tests/test_actors.c`。

目标：按批准范围更新 Boss/学生位置、归一化移动、有效受击、无敌和倒下状态。输入是意图与命中事件，不能读取键盘或 EasyX。

验收：松开停止、斜向同速、边界不越界、无敌时不重复扣血、倒下只一次、死学生不继续行动。终局由母代理 `world` 集成，不在这里宣布整局结束。

### S05 弹池和弹运动

文件：`core/projectiles.c`、`tests/test_projectiles.c`。

目标：固定容量弹池、唯一 ID/世代、阵营/来源/attack ID、前后位置、批准的运动、寿命和移除。不擅自决定场力或穿透规则。

验收：容量不足有诊断，复用无 ID 混淆，出界/寿命正确；只清指定攻击的弹不影响学生反击弹；高速运动可供 S03 检查。禁止把渲染坐标当真实世界位置。

### S06 能量与单招状态机

文件：`core/attack.c`、`tests/test_attack.c`。

目标：合法性检查、选择最近存活目标、生成/保存计划、原子接受与扣能量、预警/攻击状态转移。按批准接口调用招式模块。

验收：不足/忙碌/无目标拒绝不扣能量，无输入等待，能量恢复封顶；同一请求不重复接受；拒绝不排队；接受后 Boss/目标移动或目标倒下不重锁；精确边界 tick 无多生成一波。不得自己改四招数值或增加冷却。

### S07 绿色圆圈招式

文件：`core/pattern_ring.c`、`tests/test_pattern_ring.c`。

目标：依据批准用途，实现带缺口分时环弹的计划生成和发射。锁定 Boss 接受时原点和完整缺口变化，不跟着 Boss 后续位置移动原点。

验收：预警和生成共用几何，有可理解的缺口和分时展开；按批准时刻检查出生安全，覆盖学生预警期间走入锁定出生位置的处理；发数、波次和方向来自配置；不是无缺口全屏环。不得修改其他招式或注册表。

### S08 课表华容道招式

文件：`core/pattern_course.c`、`tests/test_pattern_course.c`。

目标：实现批准区域的封路弹带和连续可达通道，锁定列、波次、通道变化计划。

验收：预警显示实际封锁位置；新旧通道有重叠或在学生速度下可达连接；安全通道不被下一波无预警突然封死；能在代表场景中造成位置改变。不要只画背景课表，必须产生核心弹幕。

### S09 一教金矿招式

文件：`core/pattern_mine.c`、`tests/test_pattern_mine.c`。

目标：实现批准的矿点和扇形攻击，支持经批准的追击/局部打击用途，锁定矿点与扇面。

验收：矿点与学生出生安全距离按批准规则和检查时刻验证，覆盖学生预警期间走入锁定矿点的处理；预警与喷发一致，扇面两侧有可达离开方向；不能在目标移动后偷偷把矿点挪到新位置。若安全限制与追击用途冲突，报告给母代理，不自行取消距离条件。

### S10 绩点淋浴招式

文件：`core/pattern_shower.c`、`tests/test_pattern_shower.c`。

目标：实现锁定方向、波次位置和缝隙的扫描弹雨，提供批准的多目标压力用途。

验收：扫描速率和间隙可配置且可达，预警如实提示展开方向；对聚拢和分散学生分别留下生成证据；不使用全屏无缝密弹伪造大招强度。每波消耗弹池容量要可兑现。

### S11 脚本 AI 学生

文件：`ai/student_bot.c`、`tests/test_student_bot.c`。

目标：先提供可复现的简单往返脚本，再提供基于当前可见弹/公开预警的有限躲避脚本；策略版本和参数固定，可切换供诊断。

验收：同观测与 bot 状态输出一致，不写世界，不读取未来波次/RNG；边缘会转向，不持续原地抖动，不拥有瞬移或额外速度；简单脚本确实可能被打中，躲避脚本不保证无敌。不同学生有独立状态，倒下一人不影响其他 bot。复杂搜索不是本任务要求。

### S12 学生反击

文件：`core/student_fire.c`、`tests/test_student_fire.c`。

目标：实现批准的瞄准方式、发射节奏和学生弹生成。反击时钟与位置来自共享核心。

验收：学生移动方向与射击方向按契约分离；瞄准只在批准时刻采样；弹实际能命中 Boss；倒下后不新发射；暂停停止计时；同 tick/零距离处理有定义。不能为方便旧代码恢复向上固定射击或加入追踪弹。

### S13 Windows 输入适配

文件：`platform/input_win.cpp`。公共接口母代理维护。

目标：连接批准的摇杆/手柄或键盘入口，生成标准化移动和一次按下请求，提供暂停、重开、退出事件给母代理入口。

验收：长按只触发一次，松开再按可再次请求；多个逻辑追赶步只消费一次；死区和斜向正确；暂停/失焦/终局后的按键不会漏到新局。只做输入，不扣能量、不控制弹幕、不改世界。

### S14 战场绘制

文件：`render/scene.cpp`。

目标：从只读 `WorldView` 绘制 Boss、学生、判定点、目标标记、弹幕、预警和受击/倒下反馈。优先程序绘制；现有设计配图不能伪装成实时战斗。

验收：危险弹、学生弹和预警靠形状/轮廓也能区分；实际判定区域与画面一致；预警读取锁定计划；不改变物理、不消耗世界 RNG。官方校徽如使用须记录实际来源和比例；素材尚未取得时明确使用临时标记，不能阻塞核心闭环。

### S15 HUD 与界面文案

文件：`render/hud.cpp`。

目标：显示 Boss 血量、共享能量、四招名称/消耗/是否可用、目标、剩余人数和逐学生生命，提供简短开始说明、暂停和结果提示。

验收：低能量/忙碌拒绝原因清楚，当前预警/攻击状态可读；胜负/平局用核心结果；界面标为“Boss demo / 脚本 AI”；不显示假的 GPA、训练次数或正在学习。中文文字不挤出边界，不遮弹幕。界面不自行裁决。

### S16 Headless 入口与记录

文件：`sim/main.c`、`sim/log.c`。

目标：提供最小无图形运行、给定配置/种子/输入重放、事件输出和状态摘要。链接共享核心，不重复实现规则。

验收：完整命令可复制，缺文件/非法配置报错；记录 build/config/策略版本、seed、tick、请求接受/拒绝、能量、命中/倒下、结果；同条件重放两次可比较；截断显示未完成。日志失败不能改变游戏随机序列或模拟结果。具体 CLI 由母代理统一，不照搬旧训练命令。

### S17 场景与 Boss 脚本对照

文件：`sim/scenarios.c`、`sim/boss_baselines.c`。

目标：建立残血目标、学生聚拢、学生分散、Boss 受围攻四类可复现场景，以及“有能量用批准小招”“等待攒批准大招”“按局势混合”的脚本基线。

验收：脚本只能通过与玩家相同的移动/请求接口行动，不能跳过预警、能量或忙碌限制；全部基线决策周期一致，等待计入决策，固定学生策略和配对种子；不得用强制四招轮流选取冒充混合策略。脚本与场景仅供开发诊断，不是训练或真人试玩结果。

### S18 核心集成回归

文件：`tests/test_world.c`、`tests/test_replay.c`。

## 十 波次和验收顺序

### 波次 0 调查和规则

母代理检查模型路由、仓库和工具；派 S01 只读审查；自己通读资料，提出剩余关键规则确认单。建立任务板、文件所有权表和拟定接口。等待规则答复期间可完成纯 C 空骨架与工具链调查。

通过条件：现状、范围、关键规则和模型能力有记录。不要让 20 个代理同时开始猜玩法。

### 波次 1 基础核心和链接

母代理冻结获准接口/配置，维护构建和最小 `world` 骨架，并创建最小 `sim/main.c`、必要日志骨架和对应链接入口，登记为自己临时独占。分批启动 S02、S03、S04、S05、S13。先让 core 作为 C 编译、headless 可链接、EasyX 窗口能打开，之后再扩展。派 S16 前，母代理停止对 `sim/main.c`/`sim/log.c` 的写入并正式移交，让 S16 扩展已有骨架。临时桩只能用于早期链接，不能作为真实玩法、命中或最终验收证据；交付前替换所有必需行为的桩。

通过条件：移动/边界/生命/弹池/碰撞有针对性证据；game 和 sim 链接同一个核心。模拟可暂用一名脚本学生，不以此作为最终 demo。

### 波次 2 先跑通一招和攻防

启动 S06、S09、S11、S12，按已完成依赖分批推进；选批准的追击招或几何最容易实现的一招先接通。启动 S14/S15 的最小版本，不等待美术完成。

母代理立即接入移动、学生反击、血量、能量、目标、预警、攻击、终局和重开；同死裁决已确认才接终局。S18 可以先审这一招的关键跨模块行为。

通过条件：玩家能打一局，命中与扣血真实发生，能演示双方胜负，暂停/重开正常。一招只是中间里程碑。

### 波次 3 补齐四招和可复现诊断

启动 S07、S08、S10，逐招集成，更新 S14/S15；启动 S16/S17，并完成 S18。各招用同一计划契约和弹池，不能合入四份互不兼容的仿真。

通过条件：四招均可用，有真实用途区别；残血、聚拢、分散、受围攻场景可复现；输入和状态错误路径通过。

### 波次 4 独立检查 打包和试玩准备

启动 S19/S20；母代理修复 P0/P1 问题，重新跑受影响检查，打包实际 executable、配置、必要素材和依赖说明。交付可玩包及真人试玩模板。环境允许时进行真实交互操作并记录；没有图形操作工具时如实写“构建/headless已验证，图形交互待真人验证”。

真人试玩不能由语言模型虚构完成。若没有用户或其他真人参与，demo 程序可以交付，但“是否有趣、是否容易理解”保持待试玩，不把缺少玩家反馈变成构建完成后的无限等待。

### 玩法诊断清单

这部分帮助发现“大问题”，不能由技术测试替代：

1. **残血学生**：小招能否以合理资源追击或收掉目标，减少后续反击？
2. **聚拢学生**：蓄能大招是否有多目标压力，收益是否值得等待？
3. **分散学生**：大招是否浪费覆盖，小招/封路是否有明确用途？
4. **受围攻 Boss**：移动和出招是否能改变局势，还是站着按一个按钮就覆盖全部需求？
5. **站桩**：Boss 在中心、边缘、角落，分别使用单招/蓄大招/混合策略；记录实际命中、双方失血和整局结果。安全通道可存在，不要求每个位置每招都进入擦弹距离，也不凭一局获胜宣布失衡。
6. **策略对照**：固定配置和学生策略，以相同场景和配对种子比较 S17 三种策略。记录机会数、等待数、接受/拒绝次数、耗能、命中/击倒、Boss失血、结果和时长。
7. **玩家理解**：真人仅看说明能否说出目标、认识能量、理解拒绝、主动决定出招或等待？如果不理解，记录具体 UI 或规则原因。

脚本对照建议每场景先跑 5 个配对种子，属于探索样本。决策周期相同；某招不可用时不能把这次当成“放弃该招”的机会。高频使用不自动说明过强，先排除 AI 几何盲区、配置错误和没有合适场景。禁止强制均匀选招、轮流出招或按选招均匀度发奖励。

如发现某招疑似全面占优，留下可复现条件和证据，先报告实现/AI问题，再提出一项可解释调参建议；需要改变关键规则时请求用户确认。原配置与候选配置分别保留，配对重测。不要为了让报告好看一次改很多数值，也不要在局内动态调平衡。

真人试玩先准备少量匿名记录，每人两局足以收集初期问题，数量按实际资源安排；原六人完整课程验收不自动成为本 demo 已完成项。问题包括“为什么现在用这一招”“为什么继续等”“哪次受击没看懂”“是否自愿再开一局”，未知写待测，不填写模拟玩家引语。

## 十一 失败处理和交付标准

指定模型不可用、认证失败、EasyX缺失、关键规则未确认、文件所有权冲突，都说明具体事实与影响。继续不依赖阻塞的工作；不要无限重试同一错误，不向用户索取可通过仓库调查得到的信息。

对实现失败，先提交最小错误日志、复现命令和相关 diff；母代理缩小问题并派原负责人修复。连续两次修复无进展时暂停该任务、核对契约并换成更小任务或独立审查，不允许靠删验收宣称成功。

问题优先级：P0 是启动失败、崩溃、数据破坏、核心循环不成立；P1 是错误扣能量、错误命中/胜负、锁定失效、重开/暂停错误、四招缺失或没有真实效果；P2 是不阻断玩法的文案、视觉和局部优化。P0/P1修复或明确报告未完成后才收尾；不把关键未知项隐藏在长文末尾。

完成时母代理必须检查所有子/孙代理已交回并停止写入，Git diff没有无关改动，必要检查针对最后一次代码版本执行。不要测试旧版本、交付新版本。

最终向用户交付：

- 工作分支/提交和 draft PR链接（已创建时），以及可运行包的实际路径或附件。
- 已验证的构建与启动命令、运行依赖、准确操作和胜负说明。
- 四招及其当前试验用途、批准规则与配置版本。
- 技术验证结果及真实证据；未执行的图形/真人检查直说待验证。
- `docs/demo-findings.md` 中的疑似玩法问题、复现、下一轮最小调整建议；结论不得超过样本。
- `docs/demo-playtest.md` 及匿名真实记录；没有真人结果时保留模板和待测状态。
- 本轮延后项，明确 demo 不等于 v3.1 全量课程交付或已通过训练/平衡验收。

现在先执行波次0，然后按已确认依赖持续推进。你的责任是完成一个用户能操作、能输赢、能重开、能检验资源与招式选择的 demo，并如实说明验证边界。
