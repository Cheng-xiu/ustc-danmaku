# 机器学习辅助平衡：实施建议

更新：2026-10-07。状态：基本玩法稳定后执行的规划，尚未训练或验证。网页技术方案已批准，训练仍使用原生 C 核心。

依赖 [Boss 基本玩法规划](boss-mode-plan.md)。目标是用 AI 寻找容易被重复利用的强招或策略，帮助编写同学定位问题、调整规则，再验证。**高频使用是线索，不能单凭次数就削弱。** 便宜招本来就更容易频繁使用；AI 也可能利用学生策略、实现或奖励的漏洞。

## 1. 三种角色分开

| 角色 | 用途 |
| --- | --- |
| 人类 Boss | 主玩法与最终试玩对象；检验操作是否轻松、目标是否明确、选择是否有意义 |
| AI 学生 | 对手；评估时保存并冻结其策略版本，避免对手同时变化导致无法比较 |
| 离线 AI Boss | 平衡测试工具；学习移动、等待蓄能与主动选招，寻找可反复获利的策略 |

先用脚本对战建立基线，再训练 AI Boss。游戏与无图形测试共用同一套逻辑与配置，不另写一套近似规则。正式游戏使用冻结版本；调参是开发阶段的版本更新，不在玩家的一局中隐藏改变招式强度。

### 网页与训练的运行边界

按 [网页 Demo 规划](web-demo-plan.md)，浏览器使用 PixiJS + TypeScript 显示和输入，游戏核心为同一 C 源码的 Wasm 构建；离线训练使用同一核心与配置的原生无界面构建。Pixi 显示刷新率、页面暂停和浏览器墙钟不决定训练步长或吞吐。

迁移阶段先核对原生/Wasm 同种子、同逐 tick 输入的状态、事件与终态。渲染快照不直接作为学习观察，脚本 sim 不等于已完成的强化学习环境；观察、动作、奖励、决策周期、重置、终止/实验截断及批量环境接口仍是后续工作。本轮不要求训练模型，也不承诺网页性能等同原生。

## 2. 执行顺序与产出

| 步骤 | 要做的事 | 必须留下的产出 |
| --- | --- | --- |
| A：固定实验条件 | 记录核心提交、规则配置、Boss／学生策略版本、训练预算和种子；分开训练、调参验证与最终验证用的种子和场景 | 一份可复跑的实验清单；每轮比较前锁定版本 |
| B：建立脚本基线 | 比较“有能量就用某小招”“等待攒大招”“按局势混合使用”，并让各脚本遵守同样的移动、预警、能量与攻击限制 | 各基线的对局结果、资源使用和回放；先排除明显规则或实现漏洞 |
| C：训练测试 AI Boss | 让策略能够选择等待或主动发招；观察至少反映能量、可用招式、双方生命、目标数量及分布、当前攻击状态 | 写明观察、动作、决策时机、奖励定义及其局限；保存策略与训练版本 |
| D：筛出可疑策略 | 按相似局势比较选择比例、消耗与实际收益，查看回放，再与脚本基线核对 | 可疑招式、适用局势、样本量、复现条件及排查结论 |
| E：调整并重测 | 开发者写出调整假设，每轮优先改一个参数；旧、新配置使用配对种子与相同冻结学生策略对照 | 一份旧／新配置对比，说明改了什么、为何改、收益和取舍如何变化 |
| F：重新学习并独立验证 | 同等预算重新训练 AI Boss；用未参与调参的种子和额外学生策略评估，再进行真人 Boss 试玩 | 新策略能否重新找到强招的结果、独立验证结果、真人体验记录；通过后冻结版本 |

算法、观察编码、奖励系数、训练预算和判定阈值在核心稳定及算力明确后确定。训练前还需明确终局与实验截断的区别及处理。原规范的 `Q[36][4]` 对应旧状态和固定选招窗口，不能直接用于新能量玩法，也不能把其检查点改名当作新模型。

奖励设计应围绕整局胜负与实际攻防结果解释，防止策略只刷命中、擦弹或其他代理指标。**不通过“强制轮流选招”或“奖励使用比例均匀”掩盖单招优势。** 若一局未结束，记录为未完成及其原因，不凭空补成胜或负。

## 3. 需要记录什么

先记录足以复现和比较的数据，不先做复杂平台。

| 记录层级 | 最少信息 |
| --- | --- |
| 实验 | 核心提交、完整规则配置及版本、策略版本、种子、场景、训练预算、训练／验证用途 |
| 决策 | 逻辑时刻、能量、合法招式、攻击状态、目标及存活学生数量、双方位置和生命、选择等待还是出招；技能启用后记录相关状态 |
| 动作与结果 | 请求是否接受及拒绝原因、实际招式与能量消耗、预警／攻击事件、命中与击倒、Boss 失血、整局结果、可复现回放标识 |

分别报告：

- **实际使用次数**：某招到底用了多少次。
- **可用时的选择比例**：在该招合法、且允许开始新攻击的决策机会中，有多少次选择了它，同时报告机会数；等待也计入决策。
- **对应收益**：结合命中、击倒、Boss 失血、耗能和整局结果查看，不能仅以命中数除能量判定优劣；控制招还要结合后续攻击与回放。

所有策略使用相同的决策机会定义，避免轮询频率改变分母。按能量余量、目标聚拢／分散、残血／满血及受围攻等局势分组比较；不把“只有小招可用”时的高占比误判为小招全面过强。

## 4. 怎样处理“AI 总用某一招”

先检查该招是否在**多个局势、种子和学生策略**下都能稳定获利，再复现只用该招的基线。排查实现错误、学生 AI 对特定几何的盲区、奖励偏差、探索不足，以及其他招式尚未学会的可能性。

如果证据指向招式本身过强，再按问题调整。例如：

| 发现的问题 | 优先考虑的调整方向 | 重测要回答的问题 |
| --- | --- | --- |
| 小招连续使用就能解决各种局势，几乎不用攒能量 | 提高消耗，或收窄覆盖／降低持续压制能力；每轮选择一个主要改动 | 小招还能追击和收残血吗？等待大招是否开始有收益？ |
| 大招对单个残血、分散目标也总是更划算 | 调整消耗、准备时间或覆盖特性，使其用途更集中 | 大招在适合的多目标场景仍有价值吗？小招是否恢复局部优势？ |
| 学生 AI 无法处理某种弹形，另一类对手可以处理 | 先修复或丰富学生策略，再重新评估招式 | 增加学生策略后是否仍占优？真人 Boss 是否仍只选该招？ |

这些是诊断后的调整选项，不是预先指定的削弱方案。对照时先观察旧策略在新配置中的表现，再重新训练，防止把“旧模型暂时不适应”误当成问题已经解决。

## 5. 完成标准与记录模板

每轮记录：**可疑策略 → 证据与复现 → 排查 → 单项修改 → 配对比较 → 重新训练 → 独立验证 → 真人试玩 → 保留或回退**。

一轮结束应能回答：原问题是否减轻；小招与大招是否仍各有用途；玩家是否理解为何现在用、为何继续攒；是否出现新的明显占优策略。报告覆盖的场景、样本和局限，不把有限实验写成“已证明不存在最优招”，不预设胜率或四招使用占比必须相等。

建议实现后将每轮清单、对比和试玩结论保存为 `docs/balance-reports/` 下的 Markdown，关联配置与代码提交。该目录是后续输出约定，本次没有实验报告或平衡结论。

方法背景：[Assessing Video Game Balance using Autonomous Agents](https://arxiv.org/abs/2304.08699) 研究用自主代理辅助游戏平衡测试，实验涉及两款平台游戏；[The Effects of Reward Misspecification](https://arxiv.org/abs/2201.03544) 讨论代理利用错误奖励的问题。它们支持把自动测试作为辅助并检查优化目标，不能证明本项目已经平衡，也不提供本游戏的最终参数。
