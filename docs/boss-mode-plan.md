# Boss 模式：基本玩法与实施建议

更新：2026-10-07。状态：当前无尽网页源码为配置 v6、Web ABI v5，单文件 HTML 离线交付方式保留。本轮加入按住预瞄、松手释放和手动方向四招；原生 13/13 与 36,010 快照 Native/Wasm 对照通过，最终真实浏览器验收状态见 [v6 登记](validation/aim-v6.md)。[v5 实测](web-balance-findings-v5.md) 只证明旧自动锁定版的样本结果；手动几何平衡、机器学习及真人试玩仍待开展。原 v5 规划已 [归档](archive/boss-mode-plan-v5-20261007.md)。

用户后续授权已经覆盖早期有限局规划：只有 Boss 死亡结束，清波继续派学生；GPA 使用累计真实击倒数的收敛函数。本文现行规则与 [规则和集中数值](demo-rules.md) 一致，旧“击倒全部学生获胜”“双倒 Boss 胜”“GPA 延后”仅作历史记录。

面向编写同学及审核的助教、老师。本规划依据完整 [v3.1 规范](project-spec-v3.1.md)、用户上传的 Boss 模式评审稿与 Demo 汇报，以及后续讨论整理。用户已明确调整的玩法以本文为准；未涉及的内容仍须核对 [原 PDF](../references/project-spec-v3.1.pdf)。上传汇报中的测试结果属于作者报告，不能视为本仓库已独立验证的结果。

## 1. 先做清楚的核心体验

**玩家操作 Boss，朝鼠标指针移动，按住技能确定方向、松开进攻，持续击倒会躲弹和反击的 AI 学生，争取更高 GPA。** 默认从 3 名学生开始；清波后显示 2 秒出生预告，下一波增加 1 人，最多 8 人，此后持续派 8 人。没有胜利条件，Boss 血量耗尽判败；同一 tick Boss 与最后学生倒下也判败。

玩家每次决策都应能回答：**现在花能量解决眼前的威胁，还是留着能量等待更好的进攻机会？** 短期目标是命中、追击、减少反击；长期目标是击倒更多学生、保持生存，并保留应对下一波的资源。GPA 仅取决于累计真实击倒数 n：`floor(430*n/(n+20))/100`，有限 n 趋近而不显示 4.30。存活时间、受伤和波次本身不加分。

当前已接入这条无尽循环、GPA 与死亡摘要，双方数值仍为集中配置的试玩起点。清波保留 Boss 血量、位置和能量并清旧弹，新生学生只按公开预告点位出现；无强制对局时限，实验截断不判胜负。校徽按官方素材以圆形遮罩显示，命中判定仍是半径 22 px 的圆。

网页采用 **PixiJS + TypeScript + C/Wasm**，具体边界、任务和验收见 [网页 Demo 规划](web-demo-plan.md)。已有纯 C 规则作为迁移基线；前端负责输入、画面和 UI，后续训练继续用同一核心的原生无界面构建。

## 2. 操作与能量规则

| 项目 | 首轮实施建议 | 可检查的结果 |
| --- | --- | --- |
| 移动 | 鼠标朝指针位置移动、接近时减速；窗口指针离开Canvas仍跟随，WASD/方向键为备用 | 斜向归一化、受核心合法边界限制；失焦/隐藏自动暂停 |
| 瞄准 | 手动方向与移动分开保存；实际屏幕鼠标移动才更新朝向，无有效鼠标朝向时用最近非零键盘方向/默认向上 | Boss 移动、穿过静止指针及窗口缩放不翻转已保存方向；预瞄时可以继续 WASD 走位 |
| 出招 | 按住数字1–4或按钮立即选择/预瞄，松开当前选择一次释放；空格取消 | 长按不自动发射、不预扣费；最新按下替换旧选择，旧松手不误发新招；按钮可拖到战场松手 |
| 能量 | 一条共享能量条，按逻辑时间自然恢复，有上限；暂停时停止恢复 | 玩家能看到当前能量、各招消耗及是否可用 |
| 消耗 | 接受一次出招请求时扣除一次能量；不足则拒绝并提示 | 不扣成负数，拒绝不扣能量；长按不产生未说明的连发 |
| 攻击流程 | 同时只进行一招：接受输入 → 预警 → 攻击 → 可再次选招；顶栏明显显示共享CD | 当前招结束前不叠加新招；拒绝不排队；不增设四套独立冷却 |
| 方向与预警 | C 纯候选提供预瞄，释放接受时锁定方向、Boss 原点、全部波次几何，实际攻击沿用同一计划 | 预瞄不消费随机数、不改已接受计划；接受后移动或转向不迁移弹道；不自动锁最近学生 |

手动瞄准已覆盖旧最近学生自动选择的实施起点，不应在修复中恢复自动目标。能量/CD未就绪时仍允许查看预瞄，松手由 C 拒绝且不排队；暂停、重开或失焦取消未提交选择。招式持续时间、消耗和恢复速度仍集中配置，当前沿用 v5；额外独立冷却留待确有需要时再讨论。

## 3. 招式要有用途差别

当前保留四招主题和公开预警契约，由同一 C 配置提供数值。用户本轮明确要求自行调试并平衡各招与难度，因此按可复现、相同条件的脚本对照调整统一配置，记录改动与取舍；不要求逐项重复确认，也不在玩家的一局中隐藏变参。下表是设计与试玩的用途检查依据，最终消耗、时长、弹速与波次数见 [规则表](demo-rules.md)。第 4 招消耗 100 是用户指定约束。

v6 四个方向玩法为：**25 能量前向 160°双弧环（2×24）**形成近中距压力；**50 能量可转向分列墙（2×24）**在方向横轴上分三带、封两留一；**20 能量 Boss 原点 40°窄扇三连（3×9）**用于集中进攻；**100 能量可转向五波投影雨**以目标 51 px 密度覆盖场地，保留逐波移动的 120 px 空带。墙/雨从方向对侧边界 inset 100 px 进入，不固定从屏幕顶部发射。

环在接受时检查任一存活学生中心距 Boss 不小于 20 px；金矿检查全部存活学生距离不小于 120 px，背后学生也参与，非法几何不扣费。环、金矿原点在接受时锁定，预警期间 Boss 继续移动也不迁移枪口。预瞄所有几何来自 C，颜色和形状不能另写一套物理规则。

v6 费用与时序沿用 v5，但几何和操作已改变。[v5 平衡实测](web-balance-findings-v5.md) 中的 1,152 局主要对照和额外尺寸诊断保持历史身份，不能推广成 v6 已经平衡。当前应先验证可复现 manual 释放、真实命中和清波，再用公开状态控制器与真人试玩核对用途差异；不强制技能均匀使用。

| 能量档位 | 应提供的主要用途 | 玩家承担的取舍 |
| --- | --- | --- |
| 低消耗小招 | 快速干扰、追击单个目标、收掉残血学生 | 立即解决局部问题，但消耗了原本可用于攒大招的能量；不应便宜到持续使用即可包办全局 |
| 中消耗招 | 封路、迫使学生改变位置，为后续攻击创造机会 | 当前直接收益可以有限，需要判断位置和后续机会 |
| 高消耗大招 | 在学生聚拢等合适局势中形成多目标压力 | 需要积攒与等待；对分散目标或单个残血目标未必划算，用完后资源余量较少 |

**仅把伤害和消耗一起放大，不足以形成取舍。** 小招、中招、大招还应在覆盖、准备时间或适用目标上形成区别。目标不是让四招使用比例相等，而是避免同一招在各种局势下都最划算；某招在适合的局势中被连续使用是合理的。

例如：眼前有残血学生，立即花能量收掉它，可以减少反击；继续蓄能则可能等到几名学生聚拢，用大招取得更大收益，但等待期间仍会承受攻击。这个例子是设计与试玩场景，不是已验证结论。

## 4. 按依赖落实

下表用于核对基本循环。已有实现优先复用，网页阶段的编码依赖和文件所有权按 [W01–W12 任务表](web-demo-plan.md) 执行，不按此表从零重写核心。

| 顺序 | 编写任务 | 完成依据 |
| --- | --- | --- |
| 1 | 核对并复用已有 Boss 移动、血量、学生反击与倒下事件，使用可复现学生脚本；保留历史回归入口 | 清波进入出生预告并继续；Boss 血量耗尽或同时双倒均判败，死亡后逻辑停止 |
| 2 | 接入方向选择/取消、C预瞄、松手释放、能量与单招流程，先让一招完整运行 | 按住不扣费，零tick也更新；资源/安全拒绝原因明确；预瞄、接受预警、扣费与实际攻击一致 |
| 3 | 核对四招及预警，按本轮授权做统一配置调参和对照 | 在追击残血、目标聚拢、目标分散、Boss 受围攻场景中比较选择；记录实际击倒、失血、耗能与清波，不以使用次数相等代替平衡 |
| 4 | 接入可复现的 AI 学生、多学生状态和无尽派出 | 每名学生独立生命与稳定 ID；3→8 人后持续派 8 人；出生与 120 tick 公开预告一致；AI 不改世界或读取未来随机结果 |
| 5 | 做最小 HUD 和真人试玩 | 首次试玩者能看懂方向/弹道与资源，能取消预瞄并边走位边瞄准；记录不理解或始终重复同一招的原因，再调整 |
| 6 | 基本循环稳定后接入 [机器学习辅助平衡流程](ai-balance-plan.md) | 能复现可疑策略、比较版本，再用真人试玩核对体验 |

本轮界面铺满视口；开局之前介绍技能及“按住预瞄、松开释放、空格取消”。局内顶部HUD明显显示能量、共享CD、技能消耗/可用状态及Boss血量、波次、击倒/GPA等必要信息，其余为战场。预瞄层在真实弹幕下面，提示区高度固定，理由变化不改变战场比例。每局按当前战场视口比例设置纯C场地，面积保持960×720；进行中改变比例时等比缩放、允许留边，保持圆形贴图、保存方向和已公开计划，重开后按新比例铺满。v5全屏结果保留历史记录，v6实际输入/布局以本轮验证登记为准；压制率与复杂四阶段成绩单延后。

站桩问题要用**实际命中、失血、击倒和死亡／实验截断结果**检查，并覆盖场地中心、边缘、角落及不同对手。安全通道可以存在；不能以“每个站位、每一招都必须有弹进入擦弹距离”代替检查，也不能凭单个种子的站桩结果就宣布整个玩法失衡。无尽模式不能把预算内存活、清波或较高 GPA 写成获胜。

## 5. 对原方案的调整与后续事项

| 原规范／评审稿内容 | 当前处理 |
| --- | --- |
| 人类控制学生、Boss 自动选招 | 主玩法改为人类 Boss 对 AI 学生；学生视角保留作测试与回归 |
| 朝向跟随移动，射击方向受移动控制 | Boss 使用独立保存的手动瞄准方向，按住预瞄/松手发射；学生仍瞄准 Boss 发射时位置，直线弹不追踪 |
| 固定六秒窗口选招、默认循环、独立冷却 | Boss 主玩法改为玩家主动发招、共享能量和单招流程；不把旧窗口节奏继续当作主玩法限制 |
| 原阶段加权 GPA、四阶段快照及压制率 | 当前只实装击倒数 GPA：`4.30*n/(n+20)`，向下保留两位；原四阶段积分和训练快照未接入 |
| 早期有限局与 v3 每杀 +0.10 | 当前清波持续派学生；只有 Boss 死亡结束，同 tick 双倒也判败；旧线性计分由 v4 收敛函数覆盖 |
| 原 Boss 状态表、奖励与模型 | 新规则改变了决策含义；按平衡流程重新定义，不能直接宣称旧模型适用 |

共享纯 C 逻辑核心、固定逻辑步进、确定性随机数、扫掠判定和预警一致性仍以完整规范为技术依据；多学生与技能的新增交互要逐项核对。AI 学生使用 `ddl 逆转` 的方向保留，但在启用前需明确多技能场叠加及逐学生受击／擦弹归属，并验证技能是否确实改善脱险，不能凭旧系数或汇报直接认定有效。

“靠近学生时恢复能量更快”只作为后续可选对照实验，先完成自然恢复版本。只有确实增加有意义的冒险与退守选择时才考虑保留，不按无意义的移动距离奖励能量。

手动版需要优先确认三件体验问题：金矿 120 px 禁用能否被新手理解；课/雨箭头能否让人理解对侧边界入场；裁剪到场地边界的预瞄线是否被误解为保证到达的射程。攻击结束清弹使后续波可达距离更短，不能单凭全长预瞄图宣布全场均会受击。建议先改善规则说明和 C 提供的显示信息，再决定是否需要新对照调参；具体审查与限制见 [v6 验证/玩法记录](validation/aim-v6.md)。

后续希望用离线训练更新更多的 AI 学生替换目前按人数递增的难度，但学生策略、训练算法、更新定义与强弱验证仍需在后续阶段设计。当前学生只有可复现脚本；不能用更多人数假称“更多迭代”，也不能按迭代数直接宣布模型更强。

本分支已复用 Windows Demo 基线完成网页最小版和单文件 HTML，运行方法与本轮证据见 [运行指南](web-demo-guide.md) 和 [工程验证](web-demo-validation.md)。历史报告及上传评审稿的测试声明不自动成为当前已验收事实；本轮自动对照仍不能替代真人易懂程度、四招用途和整体体验的试玩。
